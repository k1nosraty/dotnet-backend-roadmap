# درس 050 — ساختار پوشه‌ای بر اساس لایه یا قابلیت

## خروجی قابل مشاهده

یک use case یکسان را در دو چیدمان مقایسه می‌کنی.
رفتار، قراردادها و namespaceها عوض نمی‌شوند؛ فقط محل فایل‌ها تغییر می‌کند.
با یک تغییر واقعی می‌سنجی کدام چیدمان یافتن فایل‌های مرتبط را آسان‌تر می‌کند.

پیش‌نیاز: [درس 049](../049-responsibilities/README.md).
قابلیت مرجع هنوز بستن تیکت با حفظ قوانین و تعارض نسخه است.
در این درس دیتابیس یا endpoint تازه اضافه نمی‌کنیم؛ هدف مقایسهٔ سازمان‌دهی کد است.

## مشکل پوشهٔ Services

فرض کن Services شامل TicketService، EmailService، DateService، SqlService و JsonService است.
نام پوشه به تو نمی‌گوید برای تغییر «بستن تیکت» کدام فایل‌ها باید بررسی شوند.
از طرف دیگر، پوشه‌ای با نام CloseTicket که Domain و SQL و HTTP را در یک کلاس مخلوط کند هم مرز ندارد.
چیدمان فایل و مرز مسئولیت دو تصمیم مرتبط اما متفاوت‌اند.

## دو نمای یک مسئله

| نقش | نمونهٔ درس ۴۹: لایه‌ای | نمونهٔ درس ۵۰: ترکیبی |
| --- | --- | --- |
| use case | Application/CloseTicket.cs | Features/CloseTicket/CloseTicket.cs |
| قرارداد مورد نیاز use case | Application/ITicketStore.cs | Features/CloseTicket/ITicketStore.cs |
| نتیجه و خروجی | Application/OperationResult.cs | Features/CloseTicket/OperationResult.cs |
| مدل مشترک تیکت | Domain/Ticket.cs | Domain/Tickets/Ticket.cs |
| adapter ذخیره | Infrastructure/InMemoryTicketStore.cs | Infrastructure/Tickets/InMemoryTicketStore.cs |

در نمونهٔ کوچک فعلی تنها یک قابلیت داریم، پس قراردادش کنار همان قابلیت است.
وقتی Rename و Close هر دو دقیقاً به قرارداد یکسان احتیاج داشتند، مالکیت و جای مشترک قرارداد را بازنگری کن.
قرارداد مشترک را بی‌دلیل در هر feature تکثیر نکن.
هر اشتراک هم الزاماً به پوشهٔ بزرگی با نام Common نیاز ندارد.

## لایه‌ای چه چیزی را آسان می‌کند؟

مرز فنی را زود می‌بینی: Domain، Application و Infrastructure.
برای یادگیری «چه کسی به چه کسی وابسته است؟» واضح است.
اما تغییر یک قابلیت ممکن است تو را میان چند پوشه جابه‌جا کند.
وقتی همهٔ handlerها در یک پوشهٔ بزرگ باشند، یافتن یک جریان دشوار می‌شود.

## قابلیت‌محور چه چیزی را آسان می‌کند؟

ورودی، هماهنگی و نتیجهٔ یک رفتار نزدیک هم‌اند.
برای کار روی CloseTicket لازم نیست تمام Application را مرور کنی.
در پروژه‌های بزرگ، اعضای تیم می‌توانند مالک یک قابلیت باشند.
با این حال، قوانین مشترک تیکت نباید در هر قابلیت یک نسخهٔ جدا پیدا کنند.
ساختار فعلی **ترکیبی** است: featureهای برنامه در یک سمت و Domain و adapterهای مشترک در سمت دیگر.
این هنوز پیاده‌سازی کامل vertical slice یا CQRS نیست؛ درس‌های بعد آن تصمیم‌ها را جدا بررسی می‌کنند.

## namespace با مسیر فایل یکی نیست

در نمونهٔ مرجع، namespace برنامه همچنان SupportDesk.Application است.
C# برای معتبر بودن namespace الزام نمی‌کند مسیر فایل همان نام را داشته باشد.
این انتخاب کمک می‌کند مقایسه فقط روی جابه‌جایی فایل تمرکز کند.
در یک تیم می‌توان قرارداد namespace مبتنی بر feature داشت؛ آن را یک‌دست و در ADR ثبت کن.
namespace به‌تنهایی جلوی دسترسی به type دیگر در همان assembly را نمی‌گیرد.

## اجرا و مقایسه

```powershell
dotnet run --project samples/48-responsibilities/SupportDesk.csproj -- --check
dotnet run --project samples/49-folders/SupportDesk.csproj -- --check
dotnet run --project samples/49-folders/SupportDesk.csproj
```

هر دو بررسی `PASS: architecture behavior` می‌دهند و اجرای عادی `Success: 1 Closed notes=1` است.
هر نمونه مستقل است؛ به سورس نمونهٔ قبلی لینک compile ندارد.
در اسکریپت `architecture_smoke.py` یکسان ماندن متن فایل‌های رفتاری دو نمونه بررسی می‌شود.
این کنترل مخصوص این جابه‌جایی آموزشی است؛ تمام refactorهای واقعی قرار نیست متن یکسان داشته باشند.
رفتار را نیز جدا اجرا می‌کنیم تا مقایسه فقط شمارش فایل نباشد.

## گام‌های refactor بدون تغییر رفتار

1. ابتدا سناریوهای درس ۴۹ را اجرا کن و نتیجه را نگه دار.
2. فایل‌های CloseTicket و قرارداد و نتیجه را زیر Features/CloseTicket منتقل کن.
3. مدل و عنوان را زیر Domain/Tickets قرار بده.
4. adapter و factory را زیر Infrastructure/Tickets بگذار.
5. namespace را ثابت نگه دار تا تغییرات اسمی با جابه‌جایی مخلوط نشوند.
6. build و بررسی را دوباره اجرا کن.
7. diff را مرور کن: رفتار یا dependency تازه‌ای نباید به تغییر پوشه چسبیده باشد.

SDK به‌صورت پیش‌فرض فایل‌های cs را در زیرپوشه‌ها پیدا می‌کند.
bin و obj خروجی ساخت‌اند و نباید به‌عنوان سورس جابه‌جا یا commit شوند.
اگر فایل قدیمی را کپی کردی اما حذف نکردی، خطای duplicate type محتمل است.

## آیا پوشه محافظ معماری است؟

خیر. یک کلاس در Features می‌تواند با نوشتن using به namespace دیگری در همان پروژه وابسته شود.
internal هم در یک assembly، تمام کد همان assembly را محدود نمی‌کند.
پس این چیدمان فعلاً قرارداد تیمی و ابزار فهم کد است.
درس ۵۱ برای enforcement از project و assembly جدا استفاده می‌کند.
حتی چند پروژه هم تمام قواعد معماری یا نشت نوع در API عمومی را خودکار بررسی نمی‌کنند.

## آزمایش هزینهٔ تغییر

دو کارت تغییر بساز:

| تغییر | فایل‌های منطقی درگیر | معیار مشاهده |
| --- | --- | --- |
| خروجی CloseTicket شامل تعداد note باشد | نتیجه و mapping use case | چند پوشه را باز می‌کنی؟ |
| تیکت بسته note تازه نپذیرد | Domain و بررسی‌ها | آیا قانون در featureها تکرار شده؟ |

تعداد پوشه کمتر به‌تنهایی معماری بهتر نیست.
هزینهٔ خواندن، تعداد دلایل تغییر و امکان بررسی قانون را با هم بسنج.
در این مرحله فایل‌ها کوچک‌اند؛ برای یک command چهار پروژهٔ مستقل نساز.

## تمرین مستقل

یک قابلیت RenameTicket کنار CloseTicket طراحی کن.
پیش از پیاده‌سازی، درخت فایل پیشنهادی را در یک Markdown بنویس.
مشخص کن کدام قرارداد مشترک است و کدام DTO مخصوص قابلیت است.
قانون عنوان معتبر و ممنوعیت تغییر تیکت بسته باید فقط در Domain باقی بماند.

### راهنمای مرحله‌ای

- ابتدا دو use case را کنار هم روی کاغذ ترسیم کن.
- برای اشتراک، نیاز واقعی callerها را مقایسه کن؛ یکسان بودن نام متد کافی نیست.
- اگر یک SharedService ساخته‌ای که HTTP و dictionary و Domain را می‌شناسد، دوباره نقش‌ها را تفکیک کن.
- برای آزمایش، رفتار را قبل و بعد با ورودی یکسان اجرا کن.

## سناریوهای خطا

- فایل هم در مسیر قدیمی و هم در مسیر تازه بماند: duplicate declaration.
- namespace همراه جابه‌جایی تغییر کند ولی usingها اصلاح نشوند: خطای type یافت نشد.
- قاعدهٔ بستن در feature کپی شود: تغییر قانون فقط یکی از مسیرها را اصلاح می‌کند.
- قرارداد عمومی به dictionary وابسته شود: تغییر adapter به لایهٔ برنامه نشت می‌کند.

## معیار عبور

- خروجی و سناریوهای شکست هر دو چیدمان برابر باشند.
- انتخاب ترکیبی خودت را با یک تغییر واقعی توضیح بدهی.
- بتوانی فرق folder، namespace و assembly را بیان کنی.
- بدانی چرا ساختار پوشه‌ای به‌تنهایی dependency نامجاز را رد نمی‌کند.
- برنامهٔ فعلی را بدون نیاز به دیتابیس از پوشهٔ نمونه اجرا کنی.
