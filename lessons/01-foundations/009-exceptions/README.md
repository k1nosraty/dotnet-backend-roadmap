## خروجی درس

خطای ورودی، نقض قانون و خرابی فایل را از هم جدا می‌کنی.
از exception درست استفاده می‌کنی و فایل باز را با using آزاد می‌کنی.
می‌توانی توضیح بدهی چرا GC جای Dispose نیست.

## پیش‌نیاز

Ticket، guard سازنده و nullable در درس‌های ۰۰۷ و ۰۰۸.
در این درس برای اولین بار یک فایل لاگ کوچک می‌نویسیم؛ ذخیرهٔ مدل در JSON درس ۰۱۱ است.

## محل اجرای قطعه‌ها

قطعه‌های این صفحه بخش‌هایی از [نمونهٔ همین درس](../../../samples/08-ticket-exceptions/Program.cs) هستند، نه چند برنامهٔ مستقل برای چسباندن پشت سر هم. کلاس Ticket در [Domain](../../../samples/08-ticket-exceptions/Domain/Ticket.cs) است و Program با `using SupportDesk.Domain;` آن را می‌شناسد. برای تغییر مثال‌ها، یک کپی از پوشهٔ همین نمونه در exercises بساز؛ فایل‌های درس ۷ را با مدل این درس مخلوط نکن.

ابتدا نمونهٔ کاملِ بخش ۱۲ را اجرا کن؛ سپس در کپی خودت هر تغییر را جدا انجام بده. در مثال فایلِ بخش‌های ۸ و ۹، پیش از usingها مسیر را تعریف کن:

```csharp
string path = "activity.log";
```

این مسیر نسبت به پوشهٔ اجرای process است. writer بخش ۸ باید بسته شود و بعد reader بخش ۹ فایل را باز کند؛ اگر فقط قطعهٔ reader را اجرا کنی، فایل ممکن است هنوز وجود نداشته باشد.

## ۱. دسته‌بندی مسئله

قبل از جدول، چهار واژه را روشن کنیم:

| واژه | منظور در همین برنامه |
| --- | --- |
| exception | شیئی که اعلام می‌کند یک عملیات نتوانسته طبق قرارداد انجام شود؛ نوع و توضیح خطا را دارد |
| throw | اعلام آن شکست و ترک مسیر عادی اجرای فعلی |
| catch | محل رسیدگی به exception سازگار؛ مثلاً نمایش پیام و تصمیم دربارهٔ ادامه |
| guard | شرط ابتدای عملیات که پیش از تغییر داده، ورودی یا وضعیت غیرمجاز را رد می‌کند |

مثلاً `"abc"` به‌جای عدد یک ورودی نامعتبر است و TryParse می‌تواند آن را بدون exception گزارش کند. اما اگر برنامه مستقیماً سازندهٔ Ticket را با عنوان `"ab"` صدا بزند، سازنده هم باید قانون خودش را حفظ کند؛ صرفاً نباید فرض کند UI قبلاً ورودی را بررسی کرده است. اینجا `throw` داخل مدل و `catch` در برنامه دو مسئولیت متفاوت دارند.

| وضعیت | ابزار اولیه |
| --- | --- |
| متن abc به جای عدد | TryParse و پیام ورودی |
| شناسهٔ ناموجود | نتیجهٔ جست‌وجو یا null |
| Close از وضعیت Open | قانون مدل و InvalidOperationException |
| عنوان نامعتبر در فراخوانی سازنده | ArgumentException |
| فایل بدون مجوز | UnauthorizedAccessException |
| مسیر یا I/O خراب | IOException یا subtype مرتبط |

همهٔ شاخه‌های منو را با throw پیاده نمی‌کنیم.
خطای قابل انتظار کاربر را می‌توان پیش از صدا زدن مدل بررسی کرد.
مدل نیز باید در برابر caller نامعتبر از قانون خود محافظت کند.

## ۲. try/catch

```csharp
try
{
    _ = new Ticket(1, "ab");
}
catch (ArgumentException)
{
    Console.WriteLine("Invalid title rejected.");
}
```

وقتی ساخت exception می‌دهد، مسیر عادی try از همان نقطه متوقف می‌شود.
catch سازگار با نوع خطا اجرا می‌شود.
_ در اینجا discard است؛ عمداً نتیجهٔ ساخت موفق احتمالی را نگه نمی‌داریم.
پس از catch، جریان می‌تواند ادامه پیدا کند.

در این مثال، خطای ساخت داخل کلاس Ticket رخ می‌دهد؛ لازم نیست کلمهٔ throw داخل خود try دیده شود تا catch کار کند. سازنده برای بررسی عنوان، متد NormalizeTitle را صدا می‌زند و عنوان دوحرفی همان‌جا رد می‌شود.

مسیر اجرا را به این ترتیب بخوان:

1. وارد try می‌شویم و ساخت Ticket را شروع می‌کنیم.
2. سازنده عنوان را بررسی می‌کند؛ طول `"ab"` کمتر از سه است، پس ArgumentException پرتاب می‌شود.
3. ساخت با موفقیت تمام نمی‌شود. خط‌های بعد از محل شکست در همان try اجرا نمی‌شوند.
4. catch با نوع ArgumentException پیدا می‌شود و `Invalid title rejected.` چاپ می‌شود.
5. پس از پایان catch، کد بعد از کل try/catch می‌تواند اجرا شود.

**پیش‌بینی کن:** اگر `"ab"` را به `"Network issue"` تغییر بدهی چه می‌شود؟ ساخت موفق می‌شود، catch اجرا نمی‌شود و از این قطعه پیامی چاپ نمی‌شود. catch بخش همیشگیِ اجرای برنامه نیست.

## ۳. قانون وضعیت

```csharp
Ticket ticket = new(1, "Network issue");
try
{
    ticket.Close();
}
catch (InvalidOperationException)
{
    Console.WriteLine($"Invalid transition rejected; status: {ticket.Status}");
}
```

Status باید Open باقی بماند، چون guard پیش از تغییر اجرا شده است.

«وضعیت» یعنی درخواست در کدام مرحلهٔ کار قرار دارد. قانون همین مدل این است: ابتدا Open، سپس با Start به InProgress، و بعد با Close به Closed می‌رویم. در قطعهٔ بالا Start صدا زده نشده است.

در [کد Close](../../../samples/08-ticket-exceptions/Domain/Ticket.cs)، شرط وضعیت پیش از انتساب Closed قرار دارد. با رد شرط، throw اجرا می‌شود و به خط تغییر Status نمی‌رسیم. گرفتن exception هم خودش وضعیت را تعمیر یا درخواست را نمی‌بندد؛ فقط به شکست رسیدگی می‌کند.

**تغییر کوچک:** در کپی تمرین، قبل از try بنویس `ticket.Start();`. این بار Close مجاز است؛ پیام catch چاپ نمی‌شود و وضعیت نهایی Closed است. برای دیدنش بعد از try/catch مقدار `ticket.Status` را چاپ کن.
پیام قابل فهم در UI نوشته می‌شود.
در یک API، تبدیل این خطا به status code در مرز وب انجام می‌شود؛ domain نباید HTTP response بسازد.

## ۴. catch دقیق

catch (Exception) همهٔ exceptionهای معمول سازگار را می‌گیرد.
اگر همه را به «عنوان نامعتبر» تبدیل کنی، خرابی storage و bug کد پنهان می‌شود.
فقط خطاهایی را بگیر که می‌توانی رفتار مشخص برایشان تعریف کنی.
در مرز نهایی برنامه می‌توان ثبت خطای غیرمنتظره و خروج کنترل‌شده داشت؛ ادامه دادن کورکورانه درست نیست.

catchهای خاص باید قبل از catch عمومی قرار بگیرند.
بعضی subclassها زیر IOException هستند؛ ترتیب گرفتن آن‌ها مهم است.

نوع exception مانند دسته‌بندی مشکل است: ArgumentException دربارهٔ argument نامعتبر، InvalidOperationException دربارهٔ عملیات نامجاز در وضعیت فعلی، و IOException دربارهٔ ورودی/خروجی فایل و مانند آن است. I/O مخفف Input/Output، یعنی ورود و خروج داده است.

مثلاً FileNotFoundException یک نوع خاص‌تر از IOException هم محسوب می‌شود. اگر رسیدگی جداگانه برایش داری، catch خاص را اول می‌نویسی؛ catch عمومی‌تر زودتر آن را نگیرد. برای هر exception در این زنجیره، اولین catch سازگار اجرا می‌شود، نه همهٔ catchها.

«مدیریت کردم» یعنی تصمیم روشنی گرفتم: دوباره ورودی بگیرم، عملیات را لغو کنم یا برنامه را با پیام مناسب تمام کنم. catch خالی فقط علت شکست را پنهان می‌کند.

## ۵. حفظ stack trace

```csharp
// داخل یک catch که نیاز به ثبت و انتشار دوباره دارد:
// throw;
```

throw; همان exception جاری را دوباره منتشر می‌کند و stack trace را حفظ می‌کند.
throw ex; می‌تواند مسیر trace را از نقطهٔ جدید تغییر بدهد.
در صورت تبدیل خطا به نوع معنی‌دار تازه، exception اولیه را inner exception نگه دار.
در درس JSON این تبدیل را می‌بینی.

stack trace فهرستی از محل‌های فراخوانی است که به خطا رسیده‌اند؛ برای این نمونه، دنبال مسیر Program، سازندهٔ Ticket و NormalizeTitle می‌گردی. نام فایل و شمارهٔ خط، وقتی اطلاعات آن موجود باشد، کمک می‌کند محل شکست را پیدا کنی. این اطلاعات برای عیب‌یابی است، نه همان پیام کوتاهی که به کاربر نشان می‌دهی.

اگر catch فقط پیام را نشان دهد و تمام شود، خطا از آنجا دوباره منتشر نمی‌شود. اگر پس از رسیدگی جزئی `throw;` بنویسی، مسئولیت تصمیم نهایی را به فراخوانندهٔ بیرونی می‌سپاری. `throw;` بدون exception جاری و بیرون catch قابل استفاده نیست. inner exception یعنی هنگام ساخت خطای جدید، خطای اصلی را هم همراهش نگه داریم تا علت اولیه گم نشود.

## ۶. finally

finally برای cleanup بعد از خروج معمول یا exception استفاده می‌شود.
return در try نیز در حالت عادی مانع finally نیست.
اما خاموشی process، قطع برق یا FailFast را تضمین‌شده ندان.
برای منابع IDisposable معمولاً using خواناتر است.

cleanup یعنی جمع‌کردن منابعی که این بخش مسئول آن‌ها بوده؛ مثلاً بستن فایل بازشده. finally مسئول «چه چیزی باید در پایان انجام شود» است؛ catch مسئول «با خطا چه کنیم» است.

| وضعیت اجرای try | catch سازگار | finally در خروج معمول |
| --- | --- | --- |
| بدون exception تمام شود | اجرا نمی‌شود | اجرا می‌شود |
| exception داشته باشد و catch آن را بگیرد | اجرا می‌شود | پس از catch اجرا می‌شود |
| exception گرفته نشود و به بیرون برود | catch نامرتبط اجرا نمی‌شود | پیش از خروج به بیرون اجرا می‌شود |

پس finally فقط برای زمان خطا نیست. البته محدودیت‌های توقف ناگهانی process که بالاتر گفتیم همچنان برقرارند.

## ۷. GC و resource

GC حافظهٔ managed دسترس‌ناپذیر را جمع می‌کند.
زمان اجرای آن قرارداد آزاد شدن فوری فایل یا اتصال نیست.
FileStream و StreamWriter به resource بیرونی و buffer مرتبط‌اند.
وقتی مالک resource هستی، باید عمر آن را روشن کنی.
Dispose برای آزادسازی مشخص resource است؛ الزاماً خود شیء managed را فوراً از حافظه حذف نمی‌کند.

در این درس دو چیز جدا داریم: شیء StreamWriter در حافظهٔ برنامه، و دسترسی به فایل که سیستم‌عامل در اختیار آن گذاشته است. تمام‌شدن استفادهٔ ما از متغیر، به معنی بسته‌شدن فوری فایل نیست.

IDisposable نام قراردادی است که متد Dispose را در اختیار مصرف‌کننده می‌گذارد: «وقتی کارت با من تمام شد، کارهای پایان استفاده را انجام بده.» برای StreamWriter، این کار شامل نوشتن داده‌های باقی‌مانده و بستن فایل است. GC یا Garbage Collector حافظهٔ managed را مدیریت می‌کند؛ منتظر GC ماندن، روش تعیین زمان بستن فایل نیست.

buffer یعنی حافظهٔ موقتی که داده ممکن است پیش از ارسال به فایل در آن نگه داشته شود. به همین دلیل موفقیت WriteLine به‌تنهایی به معنی موفقیت همهٔ کارهای پایان نوشتن نیست.

## ۸. using block

```csharp
using (StreamWriter writer = new(path, append: true))
{
    writer.WriteLine("Viewed ticket #1");
}
```

با پایان block، Dispose فراخوانی می‌شود؛ مسیر exception هم در خروج معمول این scope پوشش داده می‌شود.
writer بیرون block در دسترس نیست.
append:true به فایل موجود اضافه می‌کند؛ false می‌تواند آن را بازنویسی کند.
برای نوشتن لاگ نمونه از append استفاده کردیم.

این چند خط را چنین بخوان:

1. `new(path, append: true)` یک StreamWriter برای مسیر path می‌سازد؛ نوع از سمت چپ مشخص است. بازکردن فایل هم ممکن است همین‌جا شکست بخورد.
2. writer نام شیئی است که از طریق آن در فایل می‌نویسیم. `WriteLine` متن و پایان خط را می‌نویسد؛ این با `Console.WriteLine` که در ترمینال چاپ می‌کند فرق دارد.
3. با خروج از آکولادهای using، اگر writer با موفقیت ساخته شده باشد، Dispose آن فراخوانی می‌شود؛ حتی اگر داخل block خطایی رخ داده باشد.

scope یعنی محدودهٔ کدی که یک نام در آن قابل استفاده است. اینجا writer فقط داخل همین آکولادها شناخته می‌شود. using خطا را catch نمی‌کند؛ کار آن مشخص‌کردن پایان استفاده از منبع است.

## ۹. using declaration

```csharp
using StreamReader reader = new(path);
Console.WriteLine(reader.ReadLine());
```

منبع تا پایان scope مالک باز می‌ماند و سپس dispose می‌شود.
این با using System.IO که namespace وارد می‌کند فرق دارد.
اگر می‌خواهی فایل پیش از مرحلهٔ بعد بسته شود، block کوچک بساز.
در نمونه، writer در block بسته می‌شود و بعد reader فایل را باز می‌کند.

StreamReader برای خواندن است. `ReadLine()` یک خط می‌خواند؛ اگر دیگر خطی باقی نمانده باشد null می‌دهد. این قطعه همهٔ فایل را یک‌باره چاپ نمی‌کند.

در شکل declaration، آکولاد جدا برای using نداریم؛ Dispose در پایان scope فعلی انجام می‌شود. در Program مرجع، scope فعلی همان block مربوط به try فایل است. بنابراین reader پس از همان WriteLine فوراً بسته نمی‌شود؛ تا خروج از آن block باز می‌ماند.

| نوشتار | کاربرد |
| --- | --- |
| `using System.IO;` | در دسترس‌گذاشتن نام نوع‌ها؛ فایل باز یا بسته نمی‌کند |
| `using (StreamWriter writer = ...) { ... }` | پایان استفاده در انتهای block اختصاصی |
| `using StreamReader reader = ...;` | پایان استفاده در انتهای scope فعلی |


## ۱۰. ownership

اگر متدی Stream ساخته باشد، معمولاً همان کد مالک بستن آن است.
اگر Stream را از بیرون دریافت کرده باشد، باید قرارداد روشن کند چه کسی آن را می‌بندد.
بستن ناگهانی resource قرض‌گرفته می‌تواند caller را خراب کند.
بعضی wrapperها گزینهٔ leaveOpen دارند؛ آن را هنگام نیاز و طبق مستندات استفاده می‌کنیم.
همهٔ کلاس‌ها IDisposable نیستند؛ Ticket را بی‌دلیل disposable نکن.

ownership یعنی مسئولیت پایان استفاده با چه کسی است. مثلاً اگر متد کمکی فقط روی reader دریافتی یک خط بخواند، ممکن است caller بخواهد خط بعدی را هم بخواند؛ بستن reader در متد کمکی این امکان را از او می‌گیرد. قرارداد متد باید این مسئولیت را روشن کند. گزینهٔ leaveOpen در wrapperهای دارای این قابلیت می‌گوید منبع زیرین را هنگام بستن wrapper باز نگه دار.

## ۱۱. شکست Dispose

نوشتن buffer نهایی هم می‌تواند خطای I/O بدهد.
پس try باید scope using را هم در بر بگیرد.
catch فقط اطراف WriteLine و بیرون گذاشتن پایان using ممکن است یک خطای مهم را نگیرد.
cleanup خودش می‌تواند خطا بدهد؛ در ذخیرهٔ فایل موقت مراقب پنهان کردن خطای اصلی خواهیم بود.

ترتیب نوشتن فایل را این‌طور ببین: ساخت writer، WriteLine، پایان using و Dispose. اگر try فقط مرحلهٔ وسط را بپوشاند، خطای مرحلهٔ اول یا آخر را همان catch نمی‌گیرد. در Program مرجع، try دور کل using قرار دارد؛ بنابراین خطای معمول I/O در این مراحل به catch مربوط می‌رسد.

## ۱۳. مسیر خراب

یک مسیر داخل پوشه‌ای که وجود ندارد بده.
متن پیام خطای نمونه این است:

```text
Log could not be opened or written.
```

کد خروج باید ۱ باشد.

کد خروج نتیجه‌ای عددی برای ترمینال یا برنامهٔ اجراکننده است؛ با متنی که چاپ می‌کنیم فرق دارد. در این نمونه صفر یعنی اجرا بدون failure گزارش‌شده و یک یعنی failure کار با فایل. گرفتن exception الزاماً کد خروج را خودکار یک نمی‌کند؛ Program با `Environment.ExitCode = 1` این تصمیم را صریح اعلام می‌کند.
با دستور زیر در PowerShell کد خروج آخرین برنامهٔ native را ببین:

```powershell
$LASTEXITCODE
```

مسیر خراب نباید به «عنوان نامعتبر» تبدیل شود.
برای آزمایش permission، مجوز فایل مهم شخصی را عوض نکن؛ از مسیر آزمایشی استفاده کن.

## تمرین مستقل

پیش از تمرین اصلی، روی کپی نمونه فقط این سه تغییر را جدا انجام بده و قبل از اجرا نتیجه را بنویس:

| تغییر | انتظار برای مقایسه پس از حدس خودت |
| --- | --- |
| عنوان `"ab"` را معتبر کن | پیام catch مربوط به عنوان حذف می‌شود |
| پیش از Close، متد Start را صدا بزن | Close موفق و وضعیت Closed می‌شود |
| مسیر فایل را داخل پوشهٔ ناموجود بگذار | پیام I/O و کد خروج ۱؛ دو بخش قبلی همچنان جدا اجرا می‌شوند |

اگر نتیجه با حدست فرق داشت، اولین خطی را پیدا کن که مسیر اجرا از آنجا عوض شده است.

به منوی Ticket گرفتن خطای تغییر وضعیت اضافه کن.
فقط تغییر مجاز را در فایل activity.log ثبت کن.
اگر لاگ شکست خورد، پیام جدا بده و توضیح بده آیا تغییر مدل را ادامه می‌دهی یا کل عملیات را شکست‌خورده اعلام می‌کنی.
این سیاست تصمیم محصول است و در README باید روشن باشد.
در نمونهٔ مرجع تغییر وضعیت و ذخیرهٔ واقعی هنوز transaction واحد نیستند.

## تمرین تکمیلی

فایلی با سه خط بساز و با StreamReader همه را بخوان.
resource را در block محدود نگه دار و پس از block فایل را دوباره برای نوشتن باز کن.
بدون catch خالی، خطای مسیر ناموجود را گزارش کن.

## سرنخ

اول قانون مدل را بدون فایل بررسی کن.
سپس تعامل فایل را اضافه کن و خطای آن را جدا مدیریت کن.
از try/catch برای جایگزین کردن if ساده استفاده نکن.

## معیار عبور

- [ ] خطای ورودی و I/O را یک پیام نمی‌کنم.
- [ ] خطای transition وضعیت را تغییر نمی‌دهد.
- [ ] معنی throw; و inner exception را می‌دانم.
- [ ] resource owned را در using می‌بندم.
- [ ] GC و Dispose را یکی نمی‌دانم.
- [ ] سیاست شکست لاگ در تمرین روشن است.
