# درس 88: پیاده‌سازی مستقل و review

یک vertical slice کوچک را مستقل پیاده کن؛ یعنی یک رفتار قابل استفاده، از دریافت HTTP تا اجرای قانون و ذخیرهٔ نتیجه، را کامل بساز. پیش‌نیاز: [درس قبل](../087-requirements/README.md). زمان پیشنهادی: دو تا چهار جلسه با تمرین مستقل.

## از یک برش شروع کن

قبل از مرجع، create/read/claim را با قرارداد درس قبل بساز. ابتدا یک درخواست ثبت و خوانده شود؛ سپس Idempotency-Key و در پایان version و رقابت را اضافه کن. کل پروژهٔ نهایی را یک‌باره کپی نکن.

واژهٔ snapshot در این درس یعنی یک نسخهٔ مستقل از نمونهٔ پروژه در همین مرحلهٔ یادگیری. این نسخه عمداً داده را فقط در حافظهٔ process نگه می‌دارد و پس از توقف برنامه آن را از دست می‌دهد. Hosting/ClosedGate.cs در اجرای عادی هیچ کاربری را تأیید نمی‌کند؛ بنابراین مسیرهای محافظت‌شده 401 هستند و health/live تنها برای بررسی host است. این درس سرویس حساب واقعی نیست. هویت آزمایشگاهی فقط داخل test assembly تزریق می‌شود؛ افزودن اعتماد به X-Test-Actor در Program راه‌حل login نیست.

فایل Application/MemoryDesk.cs داخل lock، تشخیص تکرار و تغییر version را اتمیک می‌کند. قفل همین process است و در چند instance یا restart دوام ندارد. پاسخ به شکل DTO ساخته می‌شود و خود entity قابل تغییرِ داخل حافظه را به caller نمی‌دهد. در نتیجه caller نمی‌تواند با تغییر شیء پاسخ، وضعیت ذخیره‌شده را بدون عبور از قواعد برنامه عوض کند. تست رقابت، یک claim موفق می‌خواهد؛ اینکه همه 200 بگیرند نشانهٔ خطاست.

فایل‌ها را به ترتیب Domain، MemoryDesk، Program و سپس تست HTTP بخوان. در review بررسی کن tenant، یعنی سازمانِ محدودهٔ داده، از actor معتبر گرفته شود. key باید برای هر owner حوزهٔ جدا داشته باشد؛ کلید یک کاربر نباید درخواست کاربر دیگری را برگرداند. همچنین پاسخ نباید به object قابل تغییر داخلی اشاره کند. پس از فهم این مرحله به snapshot مستقل ۸۹ برو؛ آن نسخه دارای login واقعی و PostgreSQL است.

تمرین مستقل: فهرست owner را با ترتیب پایدار و size محدود اضافه کن؛ peer و tenant دیگر را تست کن. معیار عبور: سه تست موجود پاس و تست مستقل جدید بدون واردکردن test header به محصول.

## پیاده‌سازی را به سه گام قابل بررسی تقسیم کن

1. ابتدا create/read را با هویت تست بساز: پاسخ create باید شناسه بدهد و read همان عنوان را برگرداند. عنوان نامعتبر نباید چیزی در حافظه ثبت کند.
2. کلید ایجاد را اضافه کن: همان actor و کلید و داده باید همان Id را بگیرند؛ همان کلید با دادهٔ متفاوت باید 409 بگیرد. یک کلید در دو حساب متفاوت، دو حوزهٔ مستقل دارد.
3. claim را اضافه کن: نسخهٔ فعلی و وضعیت Open را زیر همان lock بررسی و تغییر بده. اگر شش کارشناس با نسخهٔ ۱ رقابت کنند، فقط یکی می‌تواند تغییر نسخه به ۲ را ثبت کند.

پس از هر گام تست همان رفتار را اجرا کن. تست `Nul_title_is_rejected_without_consuming_the_idempotency_key` یک مرز دیگر را روشن می‌کند: ورودی خراب باید 400 بگیرد و اصلاح همان ورودی با همان کلید هنوز بتواند 201 بگیرد. رد ورودی نباید به‌عنوان ایجاد موفق در حافظه ثبت شود.

## مرور را با دو شاهد شروع کن

در [تست HTTP](../../../tests/088-prototype/PrototypeTests.cs) این دو مسیر را دنبال کن:

1. `Normal_host_never_trusts_test_identity_header`: host عادی ساخته می‌شود؛ X-Test-Actor فرستاده می‌شود ولی 401 می‌گیریم. پس header، ورودی ورودِ محصول نیست.
2. `Idempotency_and_cross_tenant_and_racing_claim_are_explicit`: فقط TestFactory هویت مصنوعی را ثبت می‌کند. همان key دوباره همان Id می‌دهد؛ actor سازمان دیگر 404 می‌گیرد؛ شش claim با version یکسان فقط یک موفقیت دارند.

قبل از اجرای تست، جدول نتیجهٔ هر درخواست را بنویس. سپس [MemoryDesk](../../../samples/87-servicedesk-prototype/Application/MemoryDesk.cs) را بخوان و مشخص کن چرا بررسی version و تغییر state باید داخل همان lock باشند. بیرون‌بردن یکی از این دو از lock، شرط و تغییر را از هم جدا می‌کند.

اگر فقط dotnet run کنی و 401 بگیری، نمونه خراب نشده است؛ برای تجربهٔ این قابلیت در این مرحله تست را اجرا کن. login واقعی در درس ۸۹ اضافه می‌شود. تمرین فهرست این درس نیز باید هویت ساختگی را فقط در تست دریافت کند.
