## مسئله را با مثال بفهم

درخواست «چاپگر قطع است» فوری است؛ مریم صاحب آن و رضا کارشناس سازمان اوست. هنگام ثبت در ساعت ۱۰، موعد ساعت ۱۴ از سرور تعیین می‌شود. رضا درخواست را می‌پذیرد، با توضیح می‌بندد و مریم یک بار باز می‌کند. کارشناس سازمان دیگر هیچ مرحله‌ای را نمی‌بیند.

اول جدول R1 تا R11 در صورت مسئله را بخوان و برای هر قانون یک ورودی، نتیجه و وضعیت ذخیره‌شده بنویس. سپس فایل Domain/DeskRequest.cs نمونه را باز کن: Open تنها نقطهٔ ساخت، Claim/Close/Reopen تنها راه‌های تغییر هستند؛ private setter مانع تغییر دلخواه state از بیرون است. Actor یک ورودی مورد اعتمادِ لایهٔ کاربرد است؛ Domain خودش token را بررسی نمی‌کند.

خروجی برنامه باید دقیقاً `state=Open; version=4; reopens=1; dueHours=4` باشد. عدد چهار از create، claim، close و reopen می‌آید؛ deadline فوری بعد از reopen از زمان تازه محاسبه می‌شود. version شمارندهٔ تغییر است و به معنی تعداد درخواست HTTP نیست.

تمرین: ساعت تست را ثابت نگه دار و موعد normal را پیش‌بینی کن؛ سپس تلاش برای reopen دوم را بنویس و ثابت کن version عوض نشده است. معیار عبور: هشت تست پاس، توضیح تک‌تک انتقال‌ها و ماتریس مجوز مستقل خودت.

## انتقال‌ها را روی کاغذ دنبال کن

| عمل | actor | نسخهٔ قبل → بعد | وضعیت بعد |
| --- | --- | --- | --- |
| Open | صاحب | — → ۱ | Open |
| Claim | کارشناس همان سازمان | ۱ → ۲ | InProgress |
| Close با توضیح معتبر | همان کارشناس | ۲ → ۳ | Closed |
| Reopen | صاحب | ۳ → ۴ | Open |

در Open نام متد به معنی «ساخت درخواست» است؛ state نیز نام Open دارد. این دو کاربرد را یکی ندان. در Claim و Close و Reopen، expected version از caller می‌آید؛ Domain فقط نسخهٔ برابر را می‌پذیرد. تصمیم HTTP مانند 403 در لایهٔ endpoint/application است، نه داخل مدل.

در [Program](../../../samples/86-capstone-contract/Program.cs) کنار هر فراخوانی، state و version را پیش‌بینی کن و سپس اجرا کن. برای مشاهدهٔ خطا، در کپی خودت نسخهٔ close را از ۲ به ۱ تغییر بده؛ باید تغییر رد شود، نه اینکه version به ۳ برسد.
