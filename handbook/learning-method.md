# روش یادگیری و معیار عبور

## چرخهٔ هر درس

1. مسئله و خروجی مورد انتظار را بخوان؛ قبل از دیدن پاسخ، راه‌حل خودت را حدس بزن.
2. نمونه را اجرا کن و مقدار متغیرها را با debugger دنبال کن.
3. تغییر کوچک اعمال کن و پیش از اجرا خروجی را پیش‌بینی کن.
4. تمرین را در پوشهٔ exercises خودت از صفر بنویس.
5. سناریوهای پذیرش و ورودی خراب را بررسی کن.
6. تصمیم‌ها را در README تمرین خودت توضیح بده.
7. در PROGRESS خطاها و پرسش‌های حل‌نشده را ثبت کن.

## معیار بررسی هر تحویل

| معیار | نشانهٔ قبول |
| --- | --- |
| رفتار | همهٔ سناریوهای پذیرش پاسخ درست دارند |
| فهم | بدون نگاه کردن به نمونه، مسیر داده را توضیح می‌دهی |
| خوانایی | نام‌ها معنی دارند و هر بخش مسئولیت مشخص دارد |
| خطا | ورودی نامعتبر رفتار تعریف‌شده دارد |
| تکرارپذیری | شخص دیگری با دستورهای README می‌تواند اجرا کند |
| تصمیم | دلیل کتابخانه یا کلاس جدید را توضیح می‌دهی |

با شکست یک معیار، تمرین اصلاح می‌شود؛ رفتن به درس بعد صرفاً با خواندن متن کافی نیست.

## روش گرفتن راهنمایی

خطای کامل، نسخهٔ SDK، دستور اجرا، ورودی و رفتار مورد انتظار را بنویس.
اول درخواست راهنمایی مرحله‌ای کن؛ پاسخ کامل را بعد از تلاش مستقل ببین.
نمونهٔ آماده، راه‌حل نمونه است و تنها معماری ممکن نیست.

## پیش‌زمینهٔ C++

شناخت شرط، حلقه و تابع کمک می‌کند؛ تفاوت reference، GC، nullable و async را از روی شباهت نام‌ها حدس نزن.
در مقایسه‌های دوره، معنی رفتار مهم‌تر از شباهت نحوی است.

## ریتم پیشنهادی

برای هر درس یک جلسهٔ فهم و یک جلسهٔ تمرین در نظر بگیر.
اگر تمرین طول کشید، همان جا بمان؛ زمان‌بندی قطعی برای حرفه‌ای شدن نداریم.
هر بخش با یک بازبینی پروژه و اصلاح کد تمام می‌شود.

## قطعه‌کد را کجا اجرا کنم؟

فرمان‌های مخزن از ریشهٔ آن اجرا می‌شوند، مگر متن صریحاً بگوید وارد پوشهٔ دیگری شو. snippet کوتاه معمولاً بخشی از فایل لینک‌شده است؛ متغیرهایی مانند tickets، path، db و token باید در همان نمونه تعریف شده باشند. همهٔ code blockهای یک صفحه را پشت سر هم در Program نچسبان؛ بعضی، نسخهٔ قبل و بعدِ یک بخش هستند.

برای تمرین، پوشهٔ نمونهٔ همان درس را در exercises کپی کن یا پروژهٔ تازهٔ مستقل بساز. فایل‌های snapshotهای مختلف را با هم جمع نکن؛ ممکن است نام کلاس یکسان ولی قرارداد و assembly متفاوت باشد. تغییرهای تمرین را با Git نگه دار تا بتوانی با مرجع همان درس مقایسه کنی.

## دو ترمینال و وضعیت محیط

سرور وب در ترمینال اول باز می‌ماند؛ درخواست HTTP را از ترمینال دوم بفرست. اجرای server و سپس curl در همان ترمینال تا وقتی server متوقف نشود ممکن نیست. متغیر محیطی هر ترمینال مستقل است؛ connection و تنظیمات host را در ترمینالی بگذار که dotnet را اجرا می‌کند.

بعد از هر آزمایش، متغیرهایی را که خودت تنظیم کرده‌ای پاک کن یا برای بخش بعد ترمینال تازه باز کن. مخصوصاً DOTNET_ENVIRONMENT، ASPNETCORE_ENVIRONMENT و تنظیمات connection می‌توانند رفتار درس بعد را عوض کنند. متغیرهای دیگر سیستم را دسته‌جمعی حذف نکن.

## نتیجهٔ تست را چگونه بخوانم؟

build یعنی کامپایل موفق؛ test یعنی اجرای assertionهای همان suite. حالت build-only، تست دیتابیس نیست؛ حالت بدون Docker هم شاهد اجرای Testcontainers نیست. خروجی NOT RUN یا skipped را پاس حساب نکن. فرمان کامل هر بخش را از فهرست همان بخش بخوان؛ نبود ابزار را با حذف تست دور نزن.

برای واژهٔ تازه، این چهار سؤال را پاسخ بده: چه مشکلی را حل می‌کند؟ کدام فایل مسئول آن است؟ چه ورودی و خروجی دارد؟ در چه حالت شکست می‌خورد؟ اگر فقط نام کلاس را حفظ کرده‌ای، یک مثال کوچک‌تر با دادهٔ خودت بساز و قبل از اجرا نتیجه را پیش‌بینی کن.
