# صورت مسئلهٔ ServiceDesk

دو سازمان مستقل از سامانهٔ پشتیبانی استفاده می‌کنند. درخواست‌کننده درخواست ثبت می‌کند؛ کارشناس همان سازمان آن را می‌پذیرد و با توضیح حل می‌بندد. صاحب درخواست فقط یک بار می‌تواند آن را باز کند. هدف، یک جریان کوچک ولی کامل و قابل اثبات است.

## قرارداد پیش از کدنویسی

| شناسه | قانون | مثال قابل مشاهده |
| --- | --- | --- |
| R1 | هویت معتبر و سازمان و مجوز از سرور | header جعلی بدون token برابر 401 |
| R2 | خواندن برای صاحب یا کارشناس همان سازمان | همکار عادی و سازمان دیگر: 404، حتی audit |
| R3 | عنوان ۳ تا ۱۲۰ Unicode scalar؛ اولویت normal یا urgent | فاصلهٔ ابتدا/انتها حذف می‌شود؛ عنوان کوتاه 400 |
| R4 | موعد با ساعت سرور؛ عادی ۲۴ ساعت و فوری ۴ ساعت | client موعد یا tenant تعیین نمی‌کند |
| R5 | کلید Guid به ازای صاحب+سازمان یکتا | ایجاد 201؛ تکرار همان payload برابر 200 و همان شناسه؛ payload متفاوت 409 |
| R6 | فقط کارشناس می‌پذیرد؛ فقط کارشناس اختصاص‌یافته می‌بندد | Open → InProgress → Closed |
| R7 | فقط صاحب، یک بار، درخواست بسته را باز می‌کند | Closed → Open؛ assignment و resolution پاک، موعد تازه |
| R8 | تغییر به version فعلی نیاز دارد | دو تغییر رقابتی با یک نسخه: یکی موفق، دیگری 409 |
| R9 | تغییر داده و audit در یک transaction | شکست ذخیرهٔ audit، خود درخواست را نیز rollback می‌کند |
| R10 | نتیجهٔ فهرست محدود و مرتب است | page از ۱ تا ۱۰۰۰۰، size از ۱ تا ۵۰؛ CreatedAt سپس Id |
| R11 | داده و Identity و key ring پس از بازیابی معتبرند | image قبلی، DB بازیابی‌شده و token قبلی |

نسخه از ۱ شروع می‌شود. بازکردن دوباره به معنی ساخت درخواست جدید نیست. تکرار create، نمایش **فعلی** همان درخواست را می‌دهد؛ پاسخ تاریخی cache نشده است. اولویت فقط هنگام ساخت تعیین می‌شود. resolution هنگام close بین ۳ تا ۵۰۰ Unicode scalar است. audit فقط شناسهٔ actor، نوع رویداد و زمان دارد؛ متن درخواست و رمز در audit نیستند.

## محدودهٔ تحویل

API شامل login، create، list، get، claim، close، reopen، audit، health و version است. ثبت‌نام عمومی، تغییر سازمان، مدیریت کارشناس، reset، refresh و ارسال ایمیل در این پروژه پیاده نشده‌اند. چهار حساب آزمایشگاهی فقط با ابزار اپراتور در دیتابیس تازه ساخته می‌شوند. token از نوع protected bearer داخلی ASP.NET Core است، JWT نیست؛ عمر پنج دقیقه دارد. پاسخ استاندارد login ممکن است refreshToken داشته باشد؛ endpoint مصرف آن نداریم و باید دوباره login کرد.

cache و queue را بدون مسئلهٔ اندازه‌گیری‌شده اضافه نمی‌کنیم. این سرویس از درس‌های قبلی برای محدودسازی و دوام استفاده می‌کند؛ تمرین توسعه می‌تواند notification با outbox باشد، ولی تحویل فعلی ادعای ارسال تضمین‌شدهٔ ایمیل ندارد.

## تصمیم معماری برای دفاع

Domain هیچ EF یا HTTP نمی‌شناسد. Application با DeskContext مستقیماً کار می‌کند؛ transaction و compare-and-swap همان‌جا هستند. این انتخاب عمداً یک vertical slice کوچک با EF به عنوان واحد کار است؛ ادعای Clean Architecture با جداسازی assemblyها نداریم. جایگزین، port و adapter مستقل است که وقتی چند storage یا policy اجباری داریم ارزش هزینه‌اش بیشتر می‌شود.

DTO عمومی با entity فرق دارد. Owner و Tenant از body پذیرفته نمی‌شوند؛ property ناشناخته 400 می‌گیرد. خواندن وضعیت فعلی کاربر از DB، لغو مجوز کارشناس را برای token قدیمی هم مؤثر می‌کند. این query هزینه دارد؛ حذفش بدون طرح revocation معادل بهبود مجاز نیست.

## تمرین مستقل

قبل از مشاهدهٔ نمونه‌ها، ماتریس owner/peer/agent/other-tenant را بنویس. سپس برای «بستن با نسخهٔ قدیمی»، «دوباره بازکردن بار دوم» و «شکست audit» نتیجه و تغییرات باقی‌مانده در DB را پیش‌بینی کن. تغییر مستقل پیشنهادی: افزودن note با همان مالکیت، transaction و تست منفی؛ از endpointهای مرجع کپی مستقیم نکن.
